# Approach to documentation

This playbook should help multidisciplinary teams find the rule, context, or next step they need quickly. The structure is opinionated on purpose: we organise by document type so the playbook can grow without turning into separate mini-handbooks for each profession.

## Core rules

- Organise by **document type first** and by subject area second.
- Give each topic **one active home**. Other pages should link to it rather than restate it.
- Write for **multi-disciplinary teams**, not a single discipline in isolation.
- Link to **canonical external sources** when the source is maintained elsewhere.
- **Take a position.** This playbook should describe the right way to do a thing, even if we change that later.
- Move superseded or historical material into **archive** so live guidance stays clear.
- **Maybe don't write anything.** Do you really need another document? 

## What goes where

| Section | Use it for |
| ------- | ---------- |
| `guides` | Active, prescriptive guidance on how teams should work |
| `references` | Factual, contextual, and decision-support material |
| `open-discussions` | Early thinking and cctive debates |
| `archive` | Historical drafts, workshop notes, and superseded material kept for context |

## How section READMEs should work

Each section README should:

- explain what belongs in the section
- link to every document in that section
- group links by user need or job to be done, not by internal team structure

Section READMEs are the main entry points for the playbook. They should be curated and useful, not placeholders.

## Writing style

- Lead with the rule, decision, or takeaway.
- Be direct about what is mandatory, recommended, or unresolved.
- Use subject-based titles and file names, not team names alone.
- Keep status and review dates current.
- Prefer short summaries and links over repeated background explanation.

## When to link out instead of duplicating

Link out when another source is already the authoritative and maintained home for the information. This includes:

- national standards and policies
- live service resources
- design histories
- external tool documentation

When linking out, add just enough context for the reader to understand why the source matters.

## Updating the playbook

If new content overlaps an existing page, improve the current page instead of creating a second version. If a page is being kept for history rather than active use, move it to `archive` and make sure the current source of truth is easy to find from the relevant section README.
